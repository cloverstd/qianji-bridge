# 04 · 协议研究方法与验证边界

本页保留历史研究的技术结论，移除了原始响应、账单数量、金额、账号特征、签名输出和主机操作记录。

## 研究路径

钱迹 macOS 客户端使用 Flutter。历史研究尝试了系统代理、pf 透明重定向、动态库注入与本地 TCP 探针，均未获得目标请求。Flutter 网络栈不一定读取系统代理；本机出站流量不能直接等同于 pf 入站转发；Hardened Runtime 限制动态注入。这些是当时环境的观察，不保证适用于所有版本。

随后参考公开项目 [fangzhengjin/qianji-mcp](https://github.com/fangzhengjin/qianji-mcp)，对客户端字符串、API 路径、签名参数做交叉核对，并进行了历史登录与查询验证。

## 保留的结论

- API 请求路径为两段，客户端画像和签名随请求一起发送。
- 错误业务参数可能返回成功信封和空数组，不能只用 HTTP 状态判断结果。
- 初始化提供账本及成员；账单同步需要完整分页、删除处理和增量游标。
- 上游大整数须无损解析；客户端 SQLite 与 REST API 的金额口径不同。
- 非空资产、借贷、标签对象和写入协议仍须独立验证，不能从空响应推断完整结构。

## 验证层次

历史协议研究、公开源码核对、当前脱敏夹具测试和真实写入测试是四种不同证据。现有自动测试仅使用人为构造的账号和账单，不证明用户账号的写入已验证。

当前适配器契约、版本差异和写入门禁见 [协议补充与验证](./06-网页版协议补充与验证.md)。本公开仓库使用全新历史，不携带原始抓包脚本或采集结果。
