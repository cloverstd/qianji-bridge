# 01 · 认证与签名

> 本文所有内容均经**实测验证**，验证环境：钱迹 4.5.2（macOS），2026-09-12。

## 1. 概览

钱迹的私有 API 没有 OAuth，也**没有开放平台**。它的认证模型是「客户端自证」：

1. 客户端把账号密码（密码先做 MD5）POST 到 `/account/login`
2. 服务端返回 `uid` 和 `utoken`
3. 后续每个请求都要带上：
   - **请求头签名**（`ctrl` / `act` / `reqidv2` / `tok`）
   - **身份凭证**（`devid` / `utoken`，部分接口还要 `htoken`）
   - **请求体身份**（`uid` / `fr`）

签名算法是逆向出来的，**没有官方文档**。它把客户端包名、时间戳和两个硬编码密钥揉进 MD5。

## 2. 基础信息

| 项目 | 值 |
|---|---|
| 生产环境基址 | `https://api.qianjiapp.com/` |
| 备用线路 | `qianji.xxoojoke.com`、`qianjiga.litangkj.com`（未实测） |
| 请求方法 | **全部为 POST**（无 GET / PUT / DELETE） |
| Content-Type | `application/x-www-form-urlencoded` |
| 路径格式 | `/{ctrl}/{act}`，**恰好两段** |
| 响应格式 | JSON，外层信封 `{ec, em, data}` |

### 路径与签名的关系

路径必须是**恰好两段**。签名算法要把这两段分别当作 `ctrl` 和 `act`：

```
/account/login     → ctrl=account, act=login
/syncv2/pull       → ctrl=syncv2,  act=pull
/category/listv2   → ctrl=category, act=listv2
```

**第三段会导致签名失败。** 参考实现里对此有显式检查并抛出 `QIANJI_SIGNATURE_ERROR`。

## 3. 签名算法

### 3.1 密钥常量

```
REQID_SECRET = "free20170908&x_*1127"
TOK_SECRET   = "michaeljackson"
```

这两个常量来自对客户端的逆向。`1172020` 和 `9081127` 是算法里另外两个魔数。

### 3.2 计算步骤

```
shiftedMs = 当前毫秒时间戳 + vs + 9081127
reqidv2   = md5( pkg + shiftedMs + ctrl + act + REQID_SECRET )

encReqid  = md5( reqidv2 + TOK_SECRET )
tok       = md5( reqidv2 + "1172020" + ctrl + encReqid + act )
```

其中 `vs` 取自客户端画像（见 3.3），当前值为 `1207`。

### 3.3 客户端画像（请求头）

以下头部**每个请求都要携带**：

| Header | 值 | 说明 |
|---|---|---|
| `ctrl` | 路径第一段 | 签名参数 |
| `act` | 路径第二段 | 签名参数 |
| `reqidv2` | 见 3.2 | 请求 ID |
| `tok` | 见 3.2 | 请求签名 |
| `devid` | 设备标识 | 登录时生成，后续保持一致 |
| `pkg` | `com.mutangtech.qianji` | 包名，参与签名 |
| `vs` | `1207` | 版本号，参与签名 |
| `vsn` | `4.5.1b3` | 版本名 |
| `os` | `1` | 平台标识 |
| `osvs` | `36` | 系统版本 |
| `clang` | `zh` | 语言 |
| `cregion` | `CN` | 地区 |
| `timezoneoffset` | `28800` | 时区偏移（秒，东八区）|
| `mk` | `beta` | 渠道标识 |
| `devbrand` / `devname` | `MCP` | 设备品牌/名称（可自定义）|

> **`pkg` 和 `vs` 参与签名计算**，改动它们会导致签名校验失败。

### 3.4 参考实现（JavaScript）

```js
const crypto = require("crypto");
const md5 = (s) => crypto.createHash("md5").update(s).digest("hex");

const REQID_SECRET = "free20170908&x_*1127";
const TOK_SECRET = "michaeljackson";
const CLIENT_PROFILE = {
  clang: "zh", cregion: "CN", timezoneoffset: "28800", os: "1", osvs: "36",
  pkg: "com.mutangtech.qianji", vs: "1207", vsn: "4.5.1b3", mk: "beta",
  devbrand: "MCP", devname: "MCP",
};

// 同一路径同一毫秒会产生相同 reqidv2，服务端会拒绝 → 必须保证毫秒递增
const lastMs = {};
function createReqidv2(ctrl, act) {
  let ms = Date.now();
  const key = ctrl + "/" + act;
  if (lastMs[key] >= ms) ms = lastMs[key] + 1;
  lastMs[key] = ms;

  const shiftedMs = ms + Number(CLIENT_PROFILE.vs) + 9081127;
  return md5(CLIENT_PROFILE.pkg + String(shiftedMs) + ctrl + act + REQID_SECRET);
}

function createTok(reqidv2, ctrl, act) {
  const encReqid = md5(reqidv2 + TOK_SECRET);
  return md5(reqidv2 + "1172020" + ctrl + encReqid + act);
}
```

### 3.5 ⚠️ 重放保护

**同一路径、同一毫秒内产生的 `reqidv2` 会被服务端拒绝。**

上例中的 `lastMs` 表就是为此存在——若当前毫秒不大于上次使用的毫秒，就强制 +1。生产实现必须做同样的去重，否则高并发下会间歇性失败。

## 4. 登录流程

### 请求

```
POST https://api.qianjiapp.com/account/login
Headers: 签名头 + devid + 客户端画像（此时还没有 utoken）
Body:
  v   = 账号（邮箱）
  pwd = MD5(密码)，UTF-8 小写十六进制
```

**密码只在本机做 MD5，明文不会发往服务端。**

### 响应（虚构示例）

```json
{"ec":200,"em":"","data":{"user":{"id":"example-user","name":"示例用户","email":"user@example.com"},"books":[],"token":"EXAMPLE_TOKEN_NOT_VALID"}}
```

**需要保存三个值**：

| 值 | 来源 | 用途 |
|---|---|---|
| `uid` | `data.user.id` | 后续请求的 body 字段 |
| `utoken` | `data.token` | 后续请求的 `utoken` 头 |
| `devid` | 客户端自生成 | 后续请求的 `devid` 头，**必须与登录时一致** |

> `devid` 由客户端生成。实测使用 `mac-<16位hex>` 格式可正常工作。同一账号换 `devid` 会表现为新设备。

## 5. 已认证请求

登录后的每个请求都要在登录请求的基础上追加：

### 请求头

```
utoken: <data.token>        # 必带
htoken: 1                   # 仅部分接口需要，见下表
```

### 请求体

```
uid = <data.user.id>
fr  = <data.user.id>        # 与 uid 同值
...业务参数
```

### 需要额外 `htoken: 1` 的接口

| 接口 | 说明 |
|---|---|
| `/syncv2/pull` | 拉取账单 |
| `/bill/syncall` | 写入账单 |
| `/tag/list` | 标签列表 |

> **注意**：`/book/list`、`/asset/list`、`/category/listv2` **不需要** `htoken`；而 `/syncv2/pull` 和 `/tag/list` **需要**。带错会导致 `ec=9002`。

## 6. 错误码

| ec | 含义 | 排查方向 |
|---|---|---|
| `200` | 成功 | — |
| `5` | `Action 'X' was not found on handler 'Y'` | 路径的 `act` 段写错。**错误信息会直接告诉你 act 名不对** |
| `8888` | 登录失败，账号和密码不匹配 | 检查账号（邮箱）与密码 |
| `9002` | 请求错误 | 参数名、参数类型、缺参，或 `htoken` 用错 |
| `400404` | verify failed (wrong) | 签名计算错误，或缺少必需头 |

`em` 字段有时是**二次编码的 JSON 字符串**，例如：

```json
{"ec":8888,"em":"{\"msg\":\"登录失败！账号和密码不匹配\"}","data":{}}
```

解析时需要对 `em` 再做一次 JSON 解析尝试。

## 7. 会话生命周期

| 项目 | 观察结果 |
|---|---|
| `utoken` 有效期 | 实测在 2026-09-12 当天持续有效。**上游实现未记录明确的过期时间**，推测为长期有效直到登出/改密 |
| `devid` 稳定性 | 同一个 `devid` 复用可持续保持登录态 |
| 重新登录 | 用相同 `devid` 重新调 `/account/login` 即可刷新 `utoken` |

### 本项目的会话策略

密码及其 MD5 仅用于当次上游认证，不持久化。token 与设备标识加密保存在服务端。凭证失效时由用户在网页重新登录，MCP 不收集账号密码。
